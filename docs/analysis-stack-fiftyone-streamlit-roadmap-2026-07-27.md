## 1. 개요

- 분석 스택은 FiftyOne(`:5153`)과 Streamlit 대시보드(`:8503`)로 구성되며, 임베딩 탐색·텍스트 검색·데이터 품질 진단·능동학습 큐 등 9개 탭이 실전 가동 중입니다.
- 다만 현재는 배포 파이프라인 밖에서 수동 운영되고 있고, 파인튜닝의 최대 병목인 **GT(Ground Truth, 사람 검수 정답 라벨) 생산 루프와 연결되어 있지 않습니다.**
- 본 계획서는 이를 해결하기 위한 **3단계 개발 계획(총 6주 + 게이트)**과 팀장 의사결정 요청 사항을 정리합니다.

## 2. 목적 — 왜 이 작업이 필요한가

### 2.1 데이터 품질 향상

CCTV 이벤트 데이터는 포지티브(화재·연기 등) 비율이 극히 낮아, **무작위로 고른 프레임을 검수하면 예산 대부분이 "배경 확인"에 소모됩니다.** 이 계획은 "무엇을 검수할지"를 데이터가 고르게 만들어 검수 1건당 품질 기여를 최대화합니다.

| 메커니즘 | 기대 효과 |
| --- | --- |
| **선별 라벨링 (AL 큐)** — 무작위 대신 희소 클래스 유사도 0.45 + 대표성 0.30 + 고유성 0.25 가중 점수로 후보를 채굴, 상위 후보의 20%는 다양성 확보용으로 강제 배분 (이미 구현·가동 중) | 검수 1건당 정보량 극대화. 다양성 강제로 "비슷한 포지티브만 반복 채굴"되는 분포 편향 방지 |
| **기존 오라벨 표면화** — 임베딩 이웃과 불일치하는 라벨을 자동 탐지하는 라벨 의심 스코어 (데이터 품질 탭) | 신규 라벨링뿐 아니라 기존 GT의 오류도 같은 검수 배선(P1-1)으로 교정 가능 |
| **GT 오염 방지** — pseudo-label QA의 스냅샷 격리 비교 + 학습 스냅샷 구성 감사 뷰(P2-2) | 모델이 만든 라벨이 사람 검수 없이 GT로 새어들어 가는 "자기학습 오염" 경로 차단 |
| **품질 계기판 (P1-2)** — GT 축적 시계열·pseudo-QA F1 추이·승격 게이트 도달 게이지 | "GT가 충분한가", "검수가 실제 탐지 품질을 올리고 있는가"를 추측이 아닌 **측정된 신호**로 판단 |

### 2.2 비용 절감

| 비용 항목 | 현재 상태 | 계획 적용 후 |
| --- | --- | --- |
| **라벨링·검수 인건** | 검수 대상 선정이 수작업 — 저비율 이벤트 특성상 검수 예산 상당 부분이 배경 확인에 낭비 | AL 선별로 같은 모델 성능 도달에 필요한 검수 건수 절감. 특히 **배선(P1-1)이 완성되어야 "AL로 아낀 라벨 수"의 계량 자체가 가능**해짐 (현재는 AL 선택이 화면에서 끝나 효과 귀속 불가) |
| **장애 대응 인건 + 다운타임** | 프로세스가 죽으면 사용자 신고까지 방치 → 수동 재기동. **작성 당일에도 컨테이너 재시작 후 두 서비스가 죽은 채 방치되어 수동 복구** | 자동 재시작(P0-2) + Slack 알림(P1-3)으로 복구가 신고 의존 수십 분 → 3분 내 SLA로. 다운타임 동안 멈추던 분석·검수 업무 중단 제거 |
| **사고 복구 비용** | 대시보드 코드가 git에 없이 컨테이너 안에만 존재 — recreate 한 번이면 라이브 코드 전체 소실, 복구는 재작성 수준 | bind mount + repo 편입(P0-1)으로 **사고 자체가 구조적으로 성립 불가능**. 코드-이미지-컨테이너 삼중 불일치 디버깅 오버헤드도 제거 |
| **유휴 인프라 기회비용** | 구축 완료된 파인튜닝 인프라(레지스트리·trainer·eval 게이트)가 GT 부족으로 **0회 가동** — 투입 비용이 매몰 상태 | GT 플라이휠이 돌아야 인프라 투자 회수 시작. eval 게이트는 잘못된 모델 승격→롤백·재학습 재작업 비용을 사전 차단 |
| **검수 부하 (중기)** | 자동 라벨 품질이 낮을수록 사람이 확인할 양 증가 | 파인튜닝된 자체 모델이 자동 라벨 품질을 올려 검수 부하 감소 — 단, 첫 학습 run 후 검증이 필요한 기대 효과 |

### 2.3 목적의 범위 (정직한 한계)

- 이 계획은 GT 생산의 **도구와 배선**을 완성합니다 — GT 자체는 검수 인력이 만듭니다(§8 의사결정 5). 도구 완성을 품질 향상의 충분조건처럼 읽지 않도록 유의.
- AL 배치를 실제 투입하기 전, **미검수 자동 라벨이 검수 완료(GT)로 승격되지 않도록 막는 무결성 게이트가 선행**되어야 합니다 (별도 수정 트랙) — 이것 없이 배선만 완성하면 플라이휠이 오염된 라벨을 더 빨리 GT로 봉인하는 역효과가 납니다.

## 3. 추진 방향

**1단계 기반 안정화(W1–2) → 2단계 GT 플라이휠(W3–6) → 3단계 학습 루프 관측(첫 학습 run 이후)**

- **기반 안정화가 모든 작업의 전제** — 분석 스택을 배포 파이프라인에 편입해 "재시작하면 죽는 수동 운영"을 종료합니다.
- **기능 개발 1순위는 능동학습(AL) 큐 → Label Studio(LS) 배선** — 라벨링 후보 계산까지 끝내 놓고 수작업에서 끊기는 GT 생산 루프의 마지막 고리를 잇습니다.

## 4. 1단계 (P0) — 기반 안정화

P0-1과 P0-2는 **같은 PR·같은 유지보수 창**으로 묶어 서비스 중단을 1회로 제한합니다.

| # | 항목 | 내용 | 공수 |
| --- | --- | --- | --- |
| P0-1 | **코드 bind mount 전환** | 대시보드 코드(`docker/analysis/*.py`)를 컨테이너에 직접 마운트하여 "git commit = 실행 코드"의 단일 진리 확립. 컨테이너에만 존재하는 파일의 repo 편입 선행 (스킵 시 코드 소실 사고) | S (1–2일) |
| P0-2 | **자동기동 + 헬스체크** | JupyterLab / FiftyOne / Streamlit 3개 프로세스를 supervisord로 컨테이너 lifecycle에 편입 — 죽으면 자동 재시작. Vertex 번역 자격증명도 이때 영구화 | M (2–3일) |
| P0-3 | **CI 편입** | analysis 코드 변경 감지 시 이미지 재빌드 + 배포 lifecycle 추가. 컨테이너 강제 재생성은 requirements/Dockerfile 변경 시에만 — `.py`는 bind mount로 무중단 반영되어 노트북 커널 끊김을 연 몇 회 수준으로 제한 | S (0.5–1일) |

**완료 기준**

- 컨테이너를 재생성해도 3개 포트가 3분 내 자동 복구
- 수동 relaunch 절차를 런북에서 삭제 가능
- 배포 후 "컨테이너 코드 = repo HEAD"가 자동 성립

## 5. 2단계 (P1) — GT 플라이휠

| # | 항목 | 내용 | 공수 |
| --- | --- | --- | --- |
| P1-1 | **AL 큐 → LS task 배선** ⭐ | Streamlit에서 라벨링 후보 선택 → 큐 테이블(PG) 기록 → Dagster가 LS task 생성 + **생성 후 실존 검증** + 상태 회신. Streamlit의 LS API 직접 호출은 금지(소유권 이원화 방지). LS task 생성기에 "임의 이미지 ID 리스트" 입력 경로 신설 필요(현행은 폴더 단위만 지원) | M+ (7–9일) |
| P1-2 | **GT 축적 KPI 탭** | 검수 완료 라벨·박스 단위 어노테이션 수 시계열 + pseudo-label QA F1 추이 + PE-Core 승격 게이트(`pe_core_min_gt`) 도달 게이지 — "GT가 언제 충분해지는가"를 팀이 같은 화면으로 공유 | M (3–4일) |
| P1-3 | **헬스체크 폴링 + Slack 알림** | 신규 모니터링 스택 도입 없이 포트 5개 폴링 스크립트 + 기존 Slack webhook 재사용 | S (1–2일) |
| P1-4 | **GPU 정비락 상태 배지** | 대시보드 상단에 GPU 정비 윈도우 상태 표시(읽기 전용) — 첫 학습 윈도우 전 필요 | S (0.5일) |

**완료 기준**

- AL 후보 선택 → LS task 실제 생성(API로 확인) → GT 증가가 KPI 탭에 보이는 루프를 1회 end-to-end 성공

## 6. 3단계 (P2) — 학습 루프 관측 & 위생

각 항목에 착수 게이트가 있어, 조건 충족 전에는 착수하지 않습니다.

| # | 항목 | 착수 조건 | 공수 |
| --- | --- | --- | --- |
| P2-1 | **eval 결과 시각화** — 신규 모델 vs 현행 모델 비교, 클래스별 오답 샘플 탐색 | 첫 학습 run 완료 후 | M |
| P2-2 | **학습 스냅샷 구성 감사 뷰** — 미검수 라벨 유입에 대한 육안 안전망 | 첫 스냅샷 생성 후 (그 전에 스냅샷 빌더에 SQL 어서션 먼저 적용) | M |

| P2-4 | **호스트 cron 인벤토리 정리** — 계정별 1회 조사 + 중복 실행 방지 확인 | 없음 | S (1일) |

## 7. 주차별 일정 (1인 순차 기준)

| 주차 | 작업 | 환경 |
| --- | --- | --- |
| W1 | P0-1 + P0-2 단일 PR → staging에서 재생성 반복 검증 | dev → staging |

| W7+ | (게이트 통과 시) 첫 스냅샷 → 첫 학습 run → P2-1/P2-2 착수 | prod GPU 창 |

## 8. 의사결정 요청 사항

| # | 결정 사항 | 내용 |
| --- | --- | --- |
| 1 | **prod 유지보수 창 지정** | W2에 analysis 컨테이너 재생성 1회 필요(5–10분, `:5153`/`:8503` 중단, 데이터는 보존). 라벨링 작업·학습 윈도우와 겹치지 않는 시간대 지정 요청 |
| 2 | **AL 배치용 LS 프로젝트 편성 규약** | 기존 폴더 단위 프로젝트에 섞을지, `al_<날짜>_<배치>` 전용 프로젝트로 분리할지. 검수자 워크플로에 직접 영향 → **라벨링 담당자 의견이 W4 설계 확정 전에 필요** |
| 3 | **eval 게이트 기준 확정 주체/시점** | 모델 승격 게이트의 margin이 아직 임시값 — 첫 학습 run 전에 확정 필요(임시값으로 첫 후보를 통과시키면 그 값이 사실상 영구 기준이 됨). `pe_core_min_gt`의 GT 집계 단위(이미지 vs 박스)도 미정 — 1,558 boxes vs 248 images로 게이트 통과 여부가 갈림 |
| 4 | **첫 학습 스냅샷 빌드 시점** | 파인튜닝 인프라(MLOps 골격)는 완성됐으나 아직 한 번도 실행 전. 이 결정이 미뤄지면 3단계 관측 기능 전체가 무기한 대기 |
| 5 | **GT 검수 인력 배정** | 도구가 W5에 완성돼도 검수 인력이 붙지 않으면 GT 플라이휠은 돌지 않음. 도구 개발과 별도의 자원 배정 필요 |
