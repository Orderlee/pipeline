01지금 실제로 열린 것 — 그리고 그 경계

"조인이 됐다"를 정확히 정의해야 다음 분석의 사거리가 나온다. 근거: Codex 코드 실사

완성된 조인의 정확한 정의는 이것이다:

(bank_version, K=1 승자 gidx)  ↔  frame id
되는 것안 되는 것 / 경계
프레임 선택 → 그 프레임들의 K=1 승자 문장 하이라이트 (그리드 체크박스 + Embeddings 선택 모두) "전체 버전" 상태의 프레임→문장 조인은 무조건 레거시 winner_gidx_v080로 폴백. 여러 버전 합산 역조인 없음
문장 클릭·lasso → 그 문장을 K=1 승자로 가진 프레임 뷰로 전환 (다중 문장 일괄) 해당 버전에 winner_gidx_*가 없으면 조인 실패. 문장→프레임은 안내가 뜨지만 프레임→문장은 조용히 빈 결과
<dataset>-prompts 짝 자동 유도 (sourcei→sourcei-prompts) 임의의 두 데이터셋 조인은 불가. 짝이 없으면 안내만
argmax_k1에서 실제 승자 문장 귀속 확인 dist_iou(제품 규칙)는 프레임 귀속이 원리적으로 없다 — 전역 LOO 기여도라 클릭·lasso 조인을 코드가 의도적으로 차단
문장별 최근접 프레임 썸네일(filepath) 이건 "그 문장이 이긴 프레임"이 아니라 코사인 최근접 예시 1장. 통계량으로 쓰면 안 됨
가장 큰 신규 자산은 아무도 아직 안 쓰고 있다. sourcei-prompts와 source-h-prompts가 같은 뱅크 v1.0.8.0을 공유한다(12,480 = 12,480, 결손 0). 즉 gidx가 두 도메인을 잇는 조인키다 — 문장 단위 완전 대응 비교가 처음으로 가능해졌다. 발견: ai-modeler

02먼저 정정할 것 — 패널 배너가 안내하는 "제품 규칙"이 틀렸다

이걸 안 고치면 다음 분석의 대조군 자체가 잘못 잡힌다.

현재 Prompt Compare 패널 배너는 대조 대상을 "제품 판정규칙 = topk_vote K=10 다수결"로 안내한다. 그런데 실제 제품 추론 코드(pe_inference/01_TuningFree_v2.py)를 확인한 결과:

제품이 실제로 하는 것파라미터
클래스별 코사인 히스토그램 → IoU(normal, event) = Σmin/Σmax--iou_mode hist --iou_hist_bins 80
IoU가 임계 미만이면 그 이벤트 발화 (다중라벨)--iou_threshold 0.15
시간 디바운스 — 최근 5프레임 중 3 이상--queue_size 5 --alarm_duration_threshold 3
추론 샘플링--model_input_fps 2
top-k / argmax / 다수결 — 코드에 0 hits. grep -n "topk\|top_k\|argmax" → 없음
결론: 제품 규칙은 dist_iou다. topk_vote K=10은 2026-08-05 이전의 오해가 남은 stale 배너다. 이 한 줄 문구 수정이 이번 작업에서 가장 비용 대비 효과가 큰 수정이다 — 안 고치면 앞으로의 모든 대조 실험이 잘못된 기준을 쓴다.

그리고 여기서 뜻밖의 수확이 나온다. 제품 추론 fps가 2인데 sourcei_build.py도 정확히 fps=2로 프레임을 추출했다. 게다가 sourcei에는 src_video · event_index · frame_in_event · t_sec이 전부 있다. source-h은 키프레임 집합이라 시간 이웃이 없어 디바운스를 코드가 명시적으로 포기했는데 — sourcei에서는 제품 규칙을 처음으로 끝까지(디바운스 포함) 재현할 수 있다.

갈린 것 2건 — 중재

⚔ sourcei에 topk_vote 점수를 백필할 것인가

ai-data-engineer + Codex: "최우선. 코드 델타 0, stage_vote 그대로 실행하면 수 분."

중재: cto가 맞다 — §02에서 확인했듯 topk_vote는 제품 규칙이 아니다. 다만 비용이 실제로 0에 가깝다(기존 npz·임베딩 재사용). 그러니 우선순위는 낮추되 부산물로 같이 돌린다. 목적은 "제품 규칙 재현"이 아니라 세 규칙이 갈리는 프레임 = 경계 사례 리뷰 큐를 얻는 것. 그 용도로는 값이 있다.

⚔ 사람 검수 표본을 몇 장, 어떤 단위로

ai-modeler: 200장 (랜덤 100 + 문장앵커 큐 100, lift 측정용)  ·  ai-data-engineer: 250~300 이벤트 (셀별 속성표본)  ·  cto: 400장 클래스 균형

중재: 숫자가 아니라 단위가 쟁점이고, 거기선 이미 합의돼 있다 — 프레임이 아니라 이벤트. 전역 오류율을 5%p 정밀도로 재려면 design effect 9.22 보정 시 3,541장이 필요해 비현실적이다. 따라서 "전역 오류율 추정"을 포기하고 "셀별 스크리닝"으로 목적을 바꾼다: 셀당 20~60 이벤트로 "이 셀은 명백히 깨졌다(≥15%)"만 판정. 총 250~300 이벤트가 착지점이고, ai-modeler의 랜덤/큐 대조 설계는 그대로 얹는다(큐의 lift를 못 재면 큐를 만든 의미가 없다).

1 · GT 신뢰도 감사 DO — 최우선

질문: gt_source별 GT 오류율은 얼마이며, 문장 앵커 큐가 랜덤 대비 몇 배 효율로 오류를 찾는가?

먼저 0원 진단. 사람을 쓰기 전에 기존 필드 교차만으로 상한/하한이 나온다:

ds.match(F("event_kind.label")=="near_miss").count_values("wave_pred_v1_0_8_0.label")
ds.match(F("event_kind.label")=="near_miss").match(F("fallen_person_count")>0).count()

뱅크(PE-Core 홀리스틱)와 SAM3(오픈보캡 검출)는 다른 모델 계열이다. 둘 다 양성인 프레임이 "GT=normal이 틀렸을" 최우선 후보. 두 값이 크게 다르면(예: SAM3 40% vs 뱅크 5%) 어느 신호를 믿을지부터 정해야 한다.

표본 설계 — 이벤트 단위, 셀별 스크리닝:

우선셀표본근거
1normal / caption / near_miss601,503장(20%). Gemini가 "넘어질 뻔"으로 판정한 경계를 코드가 강제로 normal에 편입 — 설계상 최대 오염원. 위 0원 진단 상위 스코어 우선
2normal / caption / other402,459장(32.8%). "이벤트 아님" 판정 자체의 신뢰도
3falldown·fire·smoke / folder+filename30 (fire는 근센서스)abnormal GT의 94% 원천. 세그먼트 경계 프레임 우선 — PAD_SEC=0.5가 이벤트 앞뒤 정상 장면을 끌어들였는지
4normal / none20 (모집단 159)캡션조차 없는 최약체
5랜덤 대조군 (층별 비례)100큐의 lift를 재려면 필수. 이게 없으면 "큐가 좋다"를 말할 수 없다
검정력을 미리 써둘 것. 셀당 n=50이면 관측 0건 시 상한 7.1%, 5건 시 CI [4.3%, 21.4%]. 즉 "10% 미만"과 "20% 초과"는 가르지만 그 사이는 못 가른다. 이걸 사전에 명시하는 게 이 분석의 방어선이다.

운영 주의 3가지:

  • LS로 보내지 마라. sourcei 프레임은 ffmpeg -ss/-to presigned-URL 추출 JPG라 image_id가 없다 → LS에서 검수해도 image_label_annotations에 투영될 자리가 없다. frames_relabel.py 패턴(FiftyOne in-place 패치)을 재사용하고, gt_audit 필드로 기록하라. 이건 GT 승격이 아니라 weak GT의 계측임을 라벨에 명시할 것.
  • 확증편향 차단 — 검수자에게 문장·예측을 숨기고 이미지 + 4지선다만. near_miss는 "판정 불가/경계" 선택지 별도.
  • 중복 방지 — (src_video, event_index)당 최대 1장. 안 그러면 근중복 10장을 10번 검수하고 n=10을 n=100으로 착각한다.

기각 조건: 큐의 lift ≤ 1.5 (랜덤과 다를 바 없음 → 조인의 이 용도는 폐기).

전례 경고: 이 코드베이스는 이미 한 번 "저마진이 라벨 의심을 예측한다"를 직접 반증했다 (AUC GT=normal 0.886 vs GT=fire 0.009, 재라벨 뒤집힘 lift 0.92배). 문장앵커 큐를 프로덕션 배정에 쓰기 전에 이 랜덤 대조로 검증하지 않으면 같은 실수를 반복한다.

2 · 크로스도메인 전이 DO — 사업 모델을 바꾸는 질문

질문: source-h에서 유익/유해로 판정된 문장이 sourcei에서도 같은 부호를 갖는가?

왜 지금: 조인 전엔 문장 통계가 프레임 필드에 녹아 있어 문장 단위 대응비교가 불가능했다. 이제 양쪽 다 문장=표본 + 동일 뱅크 → 12,480쌍 완전 대응.

결정 변화: 전이되면 뱅크 큐레이션은 전역 1회로 끝나고 신규 현장은 무비용 온보딩. 전이 안 되면 원가가 O(현장 수) — 사업 모델 자체가 달라진다.

설계: 주 지표는 wave_gain의 클래스 내 Spearman ρ. 클래스 간 통합 금지(문장 수가 normal 10,703 vs falldown 160이라 ΔIoU 스케일이 달라 Simpson 역설).

이 분석의 핵심 방어 — 감쇠 보정. 각 도메인 내부에서 영상 반분해 wave_gain을 두 번 계산 → 도메인 내 재현성 rA, rB. 판정은 raw ρ가 아니라 ρ / √(rA·rB). 이걸 안 하면 "전이 안 됨"과 "지표가 원래 노이즈"를 구분할 수 없다. 비용은 wave 4회.

사전 임계: 보정 ρ ≥ 0.5 → 전역 큐레이션 / 0.2–0.5 → 코어+현장 보정 하이브리드 / < 0.2 → 현장별.
기각 조건: 비캡션 층(folder+filename 2,983장)에서 부호 뒤집힘, 또는 재현성 r 자체가 0.3 미만(→ 지표를 먼저 고쳐야 함).

3 · 디바운스 재현 DO — 제품 규칙 최초 완전 재현

질문: 디바운스(최근 5 중 3)를 넣으면 wave 성능이 어떻게 변하고, 어떤 문장이 "고립 발화 생성기"인가?

왜 지금: source-h은 키프레임 집합이라 시간 이웃이 없어 코드가 디바운스를 명시적으로 포기했다. sourcei는 src_video + event_index + frame_in_event + t_sec이 있고 추출 fps가 제품 추론 fps와 동일한 2다. 조인의 기여는 죽은 발화의 승자 문장 집계 — 문장 큐레이션에 "지속성" 축이 추가된다.

결정 변화: 지금까지의 모든 수치는 "디바운스 이전"이라 제품 실측이 아니었다. 이게 되면 처음으로 제품 성능을 인용할 수 있고, 큐레이션 기준이 정확도 → 정확도 + 지속성 2축이 된다.

설계: 디바운스 전/후 per-class P/R/F1, src_video 블록 부트스트랩. 이벤트 단위 지표(이벤트당 1회 이상 발화)를 프레임 단위와 나란히 보고 — 제품 알림은 이벤트 단위다. 3/5, 2/5, 3/7 민감도 스윕.

교란: 프레임이 이벤트 구간에서만 추출됐다면 normal 시퀀스가 짧아 FP 쪽 디바운스 이득이 과대평가된다 → event_kind=other/near_miss 구간 프레임 수를 먼저 확인(선행 0), 부족하면 결론을 재현율 영향에만 한정.
기각 조건: 이벤트당 프레임 중앙값 < 5.

4 · 삭제 레버를 wave로 재현 DO — kill-or-confirm

질문: top-k 기준 "삭제 레버"(v080 문장 1.6% 제거 → 92.4% > 전면교체 91.1%)가 제품 규칙에서도 유효한가?

왜 중요: 버전 비교에서 이미 전례가 있다 — 같은 개선이 top-k에서 macroF1 +19pp였는데 wave에서는 +2.9pp로 6.5배 증발했다. 삭제 레버도 증발하면 지난 큐레이션 분석 전체가 제품 무관 결론이 된다. 신규 데이터 0으로 프로그램 전체를 검증하는 실험.

구조적 근거(왜 다를 수 있나): top-k에서 "한 번도 안 이긴 문장 삭제"는 거의 no-op이지만, wave는 클래스별 코사인 히스토그램 전체를 쓰므로 모든 문장이 판정에 기여한다 — 특히 normal 문장 10,703개가 기준 분포를 만든다(top-k에서는 거의 역할이 없던 것들). 삭제의 의미가 구조적으로 다르다.

설계: 채택 문장 내 wins 순위 ↔ wave_gain 순위 클래스 내 Spearman. wave_vs_topk가 세팅된 프레임의 승자 문장이 wave_role 하위 10%에 몰리는지 순열검정 10,000회. 동일 프레임·동일 뱅크 대응비교라 카메라 교란이 원리적으로 상쇄된다.
기각 조건: 클래스 내 ρ > 0.7이면 "정렬됨"으로 종료(좋은 결과지만 후속 없음).

5 · near_miss 감사 DO — 처방 자체가 갈린다

질문: 전체 falldown FP 중 event_kind=near_miss가 차지하는 점유율은?

왜 지금: 오탐 프레임의 승자를 자유텍스트로는 특정 못 했다. winner_gidx → 문장 → peak_word / bg_phrase / ablate_role로 원인 조각까지 내려가는 경로가 조인으로 처음 열렸다.

결정 변화: near_miss가 FP의 과반이면 처방은 임계 조정도 문장 절제도 아니라 GT를 3-state(alert / near / normal)로 재정의하는 것이다.

설계: 대조군 event_kind ∈ {other, drop}(2,635장). 1차 결정값은 비율이 아니라 점유율. src_video 블록 부트스트랩. 두 규칙 병기.
주의: near_miss 판정 자체가 캡션 정규식("뻔") 파생이라 대부분 gt_source=caption에 몰려 있다. 여기서 나오는 FP는 성능 지표가 아니라 라벨 경계 비용으로 프레이밍하고, "near_miss 정의의 정확도"는 분석 1 표본에서 별도 측정.

6 · linear probe 스케일링 커브 DO — 프로그램 존속 질문

질문: 같은 400장으로 linear probe를 학습하면(4/16/64/400-shot) 뱅크를 이기는가?

왜: 무학습 프롬프트-온리 전략의 천장은 클래스당 라벨 4장 수준이라는 게 CLIP 원논문의 결과이고, 우리 실측 +7pp가 정확히 그 대역에 있다. 400장 probe가 뱅크를 이기면 뱅크 큐레이션을 계속할지 말지가 바뀐다. GT 감사의 부산물로 거의 공짜로 나온다 — 같은 400장을 두 번 쓰는 설계다.
