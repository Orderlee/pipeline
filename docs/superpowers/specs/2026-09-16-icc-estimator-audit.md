# ICC 추정량 감사 — G1·G3 가드레일이 무엇을 재고 있나

> 2026-09-16 · [분석 계층 표준화 설계](2026-09-16-analysis-standardization-design.md) Phase 2 선행 조사
> 모든 수치는 이 세션에서 라이브/구코호트 양쪽에 직접 돌려 얻었다.

## 결론 한 줄

**G3 의 evidence 문자열은 stale 코호트(7,498) 기준이고, 라이브(6,032)에서는 재현되지 않는다.**
라이브에서 실제로 발동하는 것은 **G1 뿐**이다. 순위표를 만들지 못하는 이유는 G3 가 아니라
**G1 의 설계효과(유효표본 31~57)** 다.

## 1. 두 ICC 는 서로 다른 양이다

| | `design_effect()` (S4 가 실제로 쓰는 것) | `r1_mixed_effects.py` (G3 evidence 0.827 의 출처) |
|---|---|---|
| 단위 | 프레임별 **정답/오답 0-1** 벡터 | **(뱅크 × 카메라) 셀의 macro-F1** |
| 모형 | 일원 ANOVA, 카메라 군집 | 랜덤절편 2수준, `σ²_u/(σ²_u+σ²_e)` |
| 뱅크 | **한 개**(`ref_bank`) | 전 뱅크 동시 |
| 묻는 것 | "이 추정치의 분산이 얼마나 부풀었나" (표집) | "카메라가 뱅크보다 얼마나 크게 흔드나" (이질성) |

G3 의 action 은 *"뱅크/모델 순위표 만들지 말 것"* — 의미상 **이질성** 질문이므로 오른쪽
추정량에 대응한다. 그런데 [`s4_stats()`](../../../docker/analysis/analysis_standard.py#L266) 는
왼쪽 값으로 G3 를 판정한다. **가드레일의 문구와 구현이 다른 양을 가리킨다.**

## 2. 실측 — 라이브 vs 구코호트

| | 라이브 `sourcei` (6,032) | 구코호트 `preds.npz` (7,498) |
|---|---|---|
| `design_effect` ICC (중앙) | **0.367** (범위 0.260~0.482) | **0.508** (범위 0.338~0.868) |
| ICC > 0.5 인 버전 | **0 / 31** | **30 / 35** |
| deff (중앙) | 148.2 (범위 105~194) | 254.7 |
| 혼합효과 ICC (macro-F1) | **0.368** | **0.730** |
| macro 정의 가능 카메라 | **6 / 15** | 10 / 15 |
| 클래스별 지원 카메라 | normal 15 · falldown 5 · fire 4 · smoke 4 | normal 11 · falldown 9 · fire 4 · smoke 4 |

**원인은 추정량 차이가 아니라 코호트 교체다.** 같은 추정량을 구코호트에 돌리면 0.508/0.730 이
나와 evidence 문자열(0.827/0.932)에 가깝다. 라이브에서는 절반으로 떨어진다.

## 3. 그래서 무엇이 발동하나

| 가드레일 | trigger | 라이브 판정 |
|---|---|---|
| **G1** 군집 표집 | `deff > 20` | **발동 · 31/31 버전** (deff 105~194 → 유효표본 **31~57**, 명목 6,032) |
| **G2** 클래스 카메라 수 | `< 5` | **발동 · fire 4/15 · smoke 4/15** (falldown 5 는 경계) |
| **G3** 이질성 | `ICC > 0.5` | **미발동 · 0/31** (최대 0.482) |

## 4. 발견된 결함 3건

### D1. G3 evidence 가 stale 이고 재측정 경로가 없다
`GUARDRAILS` 의 `evidence` 는 **문자열 상수**다. 코호트가 바뀌어도 갱신되지 않고, 그 값을
읽은 사람이 라이브 판정으로 오해한다. (이 세션에서 실제로 그렇게 오해했다 — `fire 4/15`
건과 동일한 형태의 사고이며, 그쪽은 우연히 라이브와 일치해서 드러나지 않았다.)

> **조치**: `evidence` 를 정적 문자열이 아니라 `{stale_evidence, live_measured, cohort, measured_at}`
> 로 바꾸고, 발동 판정 옆에 **측정 시점의 라이브 값**을 같이 싣는다.

### D2. `s4_stats()` 가 `ref_bank` 한 개로만 계산한다
라이브에서도 deff 가 버전에 따라 **105 ~ 194 (1.85배)** 로 흔들린다. 즉 보고되는 유효표본이
`ref_bank` 를 무엇으로 고르냐에 따라 **57 vs 31** 로 달라진다. 구코호트에서는 더 심해서
ICC 0.338~0.868 이라 **ref 선택이 G3 발동 여부 자체를 뒤집었다**(30/35 가 threshold 초과).

> **조치**: S4 는 전 버전의 deff/ICC **분포**(min·median·max)를 보고하고, 가드레일 판정은
> 임의의 한 버전이 아니라 **분포 기준**(예: median 또는 worst-case)으로 내린다.

### D3. 혼합효과 ICC 가 카메라 절반 이상을 조용히 버린다
라이브에서 macro-F1 이 정의되는 카메라는 **6/15** 뿐이다(나머지는 이벤트 클래스가 없어
`macro_present` 가 빈 `present` 를 반환). 9대를 버리고 적합한 값인데 그 사실이 산출물에
남지 않는다. G2·G5 와 직접 상호작용한다.

> **조치**: 혼합효과 ICC 를 낼 때 `n_cameras_used / n_cameras_total` 을 **반드시 병기**하고,
> 사용 카메라가 절반 미만이면 그 값으로 게이트 판정을 하지 않는다.

## 5. S6-lite 결정에 미치는 영향 — 없음 (근거만 교체)

| | 이전에 내가 든 근거 | 정정 후 |
|---|---|---|
| 1차 | ~~G3 발동 (ICC 0.827)~~ | **G1 발동** — deff 105~194, 유효표본 31~57 |
| 2차 | 상위 8버전 인접 델타 CI 전부 0 포함 (직접 실측) | **동일 — 변함없음** |

명목 6,032장이 통계적으로 **40장 안팎**이다. 그 위에서 31개(고유 24개) 버전의 순위를 매기는
것은 어느 추정량을 쓰든 성립하지 않는다. **S6-lite 를 유지한다.**

## 6. 설계서에 반영할 것

- §4.4 의 "G2·G3 발동 시 후보 판정도 보류" → **"G1·G2 발동 시"** 로 교체 (G3 는 라이브 미발동)
- Phase 2 에 D1·D2·D3 조치를 작업 항목으로 편입
- 가드레일 evidence 의 stale 문제는 §1.1 "표준이 stale 위에서 돈다"의 **세 번째 사례**로 추가
