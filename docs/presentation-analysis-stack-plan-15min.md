## ② 문제 (2:00–5:30) — "왜 지금 해야 하나"

**핵심 한 줄**: 병목은 두 개다 — (1) 학습에 쓸 정답 데이터(GT)가 안 만들어지고 있고, (2) 이 도구 자체가 수동 운영이라 죽으면 방치된다.

### 병목 1: GT 부족 (품질 축)

**말하기 예시**:
> "CCTV 데이터의 특성상, 화재나 쓰러짐 같은 진짜 이벤트는 전체 영상의 극히 일부입니다. 그래서 무작위로 골라서 사람이 검수하면, 검수 시간 대부분이 '아무 일도 없는 배경 확인'에 낭비됩니다. 비유하자면 **모래사장에서 무작위로 모래를 퍼서 금을 찾는 것**과 같습니다. 저희에겐 금속탐지기 — 즉 능동학습(AL) 탭이 이미 있는데, 탐지기가 울려도 그걸 검수자에게 전달하는 배선이 없어서 못 쓰고 있는 상태입니다."

> "숫자로 보면 이렇습니다. 자동 생성 라벨은 **45만 건**이 넘는데, 사람 검수까지 끝난 라벨은 **288건 — 0.06%**입니다. 학습에 쓸 수 있는 GT는 이미지 248장, 박스 1,558개가 전부입니다. 그 결과 파인튜닝 인프라(모델 레지스트리, 트레이너, 평가 게이트)는 구축이 끝났는데 **한 번도 가동을 못 했습니다.** 실제로 모델 레지스트리 테이블은 오늘 기준 0행입니다. 투자한 인프라가 놀고 있는 겁니다."

### 병목 2: 수동 운영 (비용 축)

**말하기 예시**:
> "두 번째 문제는 더 현실적인데요, 이 대시보드들이 배포 파이프라인 밖에서 수동으로 떠 있습니다. 세 가지 위험이 있습니다.
> 첫째, **프로세스가 죽으면 아무도 모릅니다.** 사용자가 '안 열려요' 하고 신고할 때까지 방치됩니다.
> 둘째, 컨테이너를 재시작하면 서비스가 죽은 채로 남아서 **매번 사람이 손으로 다시 띄워야** 합니다.
> 셋째, 코드 관리가 삼중으로 어긋나 있습니다. 컨테이너 안 런타임 파일 9개 중 이미지에 정식으로 들어가는 건 **2개뿐**이고 나머지는 수동 복사본입니다. 심지어 유틸 2개는 git에 아예 없어서, 컨테이너를 갈아엎으면 그 코드는 복구 불가로 소실됩니다. 지금은 우연히 git과 동기화돼 있지만 구조적으로 언제든 어긋날 수 있는 상태입니다."

**짚을 포인트**:
- 여기까지 듣고 나면 청중이 "그래서 뭘 하겠다는 건데?"가 궁금해진 상태 — 그때 로드맵으로 전환

## ③ 해법: 3단계 로드맵 (5:30–11:00)

**핵심 한 줄**: 기반을 먼저 안전하게 만들고(P0) → GT 생산 루프를 연결하고(P1) → 학습이 시작되면 그걸 관측한다(P2).

**말하기 예시 (전체 구조)**:
> "3단계입니다. 순서가 중요합니다. **집을 고치기 전에 지반부터 다지는 순서**입니다."

### P0 — 기반 안정화 (W1–2, 약 1.5분 설명)

| # | 항목 | 쉬운 설명 |
|---|------|-----------|
| P0-1 | 코드 bind mount | 컨테이너 안에만 있는 코드를 git 저장소로 편입 → "git에 커밋된 것 = 실행되는 것" 단일 진리 확립. **코드 소실 사고가 구조적으로 불가능해짐** |
| P0-2 | 자동 재기동 + 헬스체크 | 3개 프로세스(JupyterLab/FiftyOne/Streamlit)를 supervisord에 편입 → 죽으면 자동으로 살아남 |
| P0-3 | CI 편입 | 코드 변경이 배포 파이프라인을 타게 함. 단 `.py` 수정은 bind mount로 무중단 반영 |

**말하기 예시**:
> "P0의 완료 기준은 명확합니다 — **컨테이너를 일부러 죽여도 3분 안에 스스로 살아나야 하고, 그 절차를 반부팅에서 역시연 가능해야 합니다.** 이게 되기 전엔 그 위에 뭘 얹어도 모래성입니다."

### P1 — GT 파이프라인 (W3–6, 약 2.5분 설명 — 발표의 하이라이트)

| # | 항목 | 쉬운 설명 |
|---|------|-----------|
| **P1-1 ⭐** | AL 탭 → Label Studio 배정 | **이 계획의 핵심.** 대시보드에서 '검수할 가치가 높은 후보'를 고르면 → 검수 도구(LS)에 작업으로 자동 배정. 지금은 후보 계산까지만 되고 사람에게 전달이 안 됨 |
| P1-2 | GT 축적 KPI 탭 | "GT가 얼마나 쌓였나, 학습 시작 가능한 수준인가"를 추측이 아닌 **측정된 그래프**로 보는 화면 |
| P1-3 | 헬스체크 폴링 + Slack 알림 | 죽으면 Slack으로 바로 알림. 대형 모니터링 스택 도입 없이 폴링 스크립트로 |
| P1-4 | GPU 정비락 상태 배지 | 학습 때문에 GPU를 비웠는지 화면 상단에 표시 (읽기 전용) |

**말하기 예시 (P1-1 강조)**:
> "P1-1이 이 계획서에서 별표가 붙은 유일한 항목입니다. 능동학습 탭이 '이 100장을 검수하면 모델이 가장 많이 배웁니다'라고 이미 계산을 해주는데, 지금 그 결과의 유일한 출구는 **CSV 파일 다운로드**입니다 — 후보 목록을 사람이 받아서 수동으로 옮겨야 하고, 실제로는 그마저도 안 쓰이고 있습니다. 이 배선을 이으면 **검수 1건당 모델 개선 기여도가 극대화**되고, 처음으로 'AL로 아낀 라벨 수'를 계량할 수 있게 됩니다."

> "설계 원칙 하나만 짚으면 — 대시보드가 검수 도구 API를 직접 호출하는 게 아니라, 중간에 Dagster를 거쳐서 생성-검증-확정 절차를 밟습니다. 소유권이 꼬이는 걸 막기 위해서입니다."

### P2 — 학습 루프 관측 (첫 학습 run 이후, 약 1분 설명)

**말하기 예시**:
> "P2는 지금 착수하지 않습니다. 각 항목에 **착수 게이트**가 있어서 조건이 충족될 때만 시작합니다. 예를 들어 '평가 결과 시각화'는 첫 학습이 실제로 돌아야 시각화할 결과가 생기니까요. 미리 만들면 상상으로 만든 화면이 됩니다."

- P2-1 평가(eval) 결과 시각화 — 신규 모델 vs 현행 모델 비교 (게이트: 첫 학습 완료 후)
- P2-2 학습 스냅샷 감사 뷰 — 미검수 라벨이 학습셋에 섞였는지 잡아내는 안전망 (게이트: 첫 스냅샷 생성 후)
- P2-3 / P2-4 — 읽기전용 자격증명 분리, 호스트 cron 인벤토리 정리 (소규모)

**짚을 포인트 (한계 — 솔직하게)**:
> "분명히 할 것은, **이 계획은 GT를 만들어주지 않습니다. GT는 검수 인력이 만듭니다.** 저희가 만드는 건 '무엇을 검수할지'를 골라주는 도구와 배선입니다. 그리고 배선만 서두르면 오히려 오염된 라벨이 정답으로 더 빨리 굳는 역효과가 있어서, 미검수 라벨이 GT로 승격되지 않게 막는 무결성 게이트가 선행되어야 합니다."

**핵심 한 줄**: 6주 + 조건부 후속. 1인 순차 기준.

| 주차 | 내용 | 환경 |
|------|------|------|
| W1 | P0-1 + P0-2 단일 PR — staging에서 재생성 반복 검증 | dev → staging |
| W2 | **prod 적용 (유지보수 창 5–10분 1회)** → P0-3 CI 편입 | main |

| W7+ | (게이트 통과 시) 첫 스냅샷 → 첫 학습 → P2-1/P2-2 | prod GPU 창 |

**말하기 예시**:
> "서비스 중단은 W2에 **딱 한 번, 5~10분**입니다. P0-1과 P0-2를 같은 PR로 묶어서 중단을 1회로 제한했습니다. 데이터는 보존됩니다. W7 이후는 일정이 아니라 조건입니다 — 게이트가 통과 안 되면 착수하지 않습니다."

## 예상 질문 & 답변 (Q&A 대비)

**Q1. "이거 하면 라벨링 비용이 얼마나 줄어드나요?"**
> "지금은 그 숫자 자체를 계산할 수 없다는 게 문제입니다. P1-1이 완성되어야 'AL로 고른 것 vs 무작위'의 효율 차이를 처음으로 계량할 수 있습니다. 계량 가능해지는 것 자체가 1차 산출물입니다."

**Q2. "6주나 걸리나요? 더 빨리 안 되나요?"**
> "실질 개발은 P1-1(7–9일)이 가장 크고, 나머지는 며칠 단위입니다. 순서를 지키는 게 핵심이라 — 기반(P0) 없이 기능부터 얹으면 지금의 '재시작하면 죽는 수동 운영' 위에 쌓게 됩니다. 1인 순차 기준이므로 인력이 붙으면 단축 여지는 있습니다."

**Q3. "AL이 고른 게 정말 좋은 후보라는 보장이 있나요?"**
> "포지티브(희귀 클래스) 유사도 0.45 + 대표성 0.30 + 고유성 0.25 가중 점수로 뽑되, 상위 후보의 최소 20%는 다양성 확보용으로 강제 배분해서 '비슷한 것만 반복해서 뽑는' 편향을 막습니다. 그리고 검수 결과가 다시 쌓이면 그 효과를 KPI 탭(P1-2)에서 검증합니다."
> (내부 참고: 대표성·고유성 점수는 FiftyOne 사전 계산 필드에서 읽어오며, 미계산 상태면 0으로 떨어져 사실상 유사도 단독 랭킹이 됨 — P1-1 착수 시 필드 계산을 배치에 포함해야 함. `fiftyone_pgvector.py:2418` 확인)

**Q4. "모델이 자기가 만든 라벨로 자기를 학습하는 오염은요?"**
> "그게 바로 '자기학습 오염 차단' 항목입니다. 모델 파생 라벨은 사람 검수를 통과하기 전엔 GT로 못 들어가게 무결성 게이트를 선행 조건으로 두었습니다. 계획서에도 '배선만 서두르면 오염 라벨이 더 빨리 GT로 굳는 역효과'를 명시했습니다."

**Q5. "P2는 왜 지금 안 만드나요?"**
> "관측할 대상(학습 결과)이 아직 존재하지 않기 때문입니다. 착수 게이트를 걸어서 조건 충족 시에만 시작합니다 — 상상으로 만든 화면은 첫 실전에서 다시 만들게 됩니다."

**Q6. "기존 검수 작업에 영향 있나요?"**
> "W2의 5–10분 중단 1회가 전부입니다. 그마저도 분석 화면만 멈추고 라벨링 도구(LS)와 파이프라인 본체는 무관합니다. AL 배치가 검수자 작업 목록에 어떻게 보일지는 결정사항 2번으로 라벨링 담당자와 함께 정합니다."

## 부록 B: 용어 한 줄 사전 (발표 중 튀어나올 때)

| 용어 | 한 줄 설명 |
|------|-----------|
| GT (Ground Truth) | 사람이 검수해서 확정한 정답 라벨. 모델 학습·평가의 기준 |
| AL (Active Learning, 능동학습) | 라벨을 달았을 때 모델 개선 효과가 가장 큰 데이터(헷갈리거나 희귀한 것)부터 골라 우선 검수시키는 기법 |
| LS (Label Studio) | 사람이 라벨을 그리고 검수하는 웹 도구 |
| FiftyOne | 이미지·라벨을 눈으로 탐색하는 데이터셋 뷰어 |
| Streamlit 대시보드 | 임베딩 검색·품질 진단 등 9개 탭짜리 분석 웹 화면 |
| eval 게이트 | 새 모델이 기존 모델보다 나은지 판정해 승격을 막거나 허용하는 관문 |
| bind mount | 호스트의 코드 폴더를 컨테이너에 직접 연결 — 컨테이너를 지워도 코드가 남음 |
| supervisord | 프로세스가 죽으면 자동으로 다시 띄워주는 관리자 |
| 스냅샷 | 학습 직전에 데이터셋을 동결한 불변 사본 — 재현성 보장 |
| pseudo-label | 모델이 자동 생성한 미검수 라벨. GT 아님 |

### AL 보충 설명 (개념 질문 대비)

> 사람 검수(라벨링)는 비싸고 느린 자원입니다. 모든 데이터에 라벨을 달 수 없으니, **어떤 데이터부터 라벨을 달지 모델이 직접 고르게** 하는 기법이 Active Learning입니다.
>
> 모델이 이미 잘 아는 데이터(예: 뻔한 배경 프레임)는 라벨을 달아줘도 배우는 게 거의 없습니다. 반대로 **모델이 헷갈려하거나, 희귀해서 본 적이 별로 없는 데이터**는 라벨 하나가 주는 학습 효과가 큽니다.
>
> 그래서 "배울 게 많은 데이터" = 좋은 데이터가 아니라 **모델의 약점을 찌르는 데이터**에 가깝습니다.
